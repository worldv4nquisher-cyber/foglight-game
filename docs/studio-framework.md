# 游戏制作团队框架

## 定位
- 类型：3D 游戏，具体内容待策划与用户共同确定
- 平台：网页 H5，桌面浏览器直接玩（2026-10-29 用户决定：不考虑手机），以后可打包成 PC
- 规模：中型项目，按版本长期迭代
- 技术栈：Three.js + TypeScript + Vite；模型用 glTF/GLB；贴图压缩（KTX2/WebP）

## 团队（4 个 Bot）
| Bot | 职责 | 产出目录 |
|---|---|---|
| 制作人（群主，兼测试） | 版本计划、里程碑、任务分派、验收；每个版本做功能测试、兼容性测试、性能测试，写 Bug 单；向用户汇报 | docs/releases, docs/tasks, docs/bugs |
| 策划 | 和用户确定游戏内容；写 GDD（玩法、世界观剧情、关卡、数值、UI 流程）；每个版本拆需求单 | docs/gdd, docs/tasks |
| 美术（兼音效） | 美术风格指南、3D 模型、贴图、角色、场景、UI、图标；音效和配乐素材 | art/, audio/ |
| 程序 | 技术框架、玩法实现、资源接入、性能优化、构建与发布 | game/ |

## 流水线（每个版本循环一次）
1. 策划和用户讨论游戏内容 → 写 GDD 草稿
2. **用户确认 GDD 定稿**（确认点 1）
3. 制作人定版本计划（docs/releases/vX.Y.md），策划把本版本拆成需求单（docs/tasks/）
4. 美术先出风格指南（第一个版本），再按需求单出资源；程序同时搭框架、实现功能，用占位资源先跑通
5. 程序接入正式资源，自测后交制作人
6. 制作人测试：功能、桌面 Chrome/Edge/Safari/Firefox 兼容、帧率（基准配置 60fps）、加载时间；Bug 写入 docs/bugs/，程序修复后回归
7. **用户试玩确认能否发布**（确认点 2）
8. 程序构建发布；制作人写版本总结，进入下一轮

## 约定
- 需求单命名：docs/tasks/vX.Y-编号-简述.md，写明负责人、验收标准
- Bug 单命名：docs/bugs/BUG-编号.md，写明复现步骤、期望、实际、严重度
- 资源命名用小写英文加短横线，如 hero-idle.glb、ui-button-start.png
- 美术和音效只用自己生成、或可商用/免版权的素材，来源记在 art/CREDITS.md、audio/CREDITS.md
- 画质往极致做，按 art/style/style-guide.md 的画质分档表控制面数和 draw call
- 代码放 game/，用 git 管理，每次交付写清楚改了什么
- 不擅自对外发布，发布前必须用户确认
